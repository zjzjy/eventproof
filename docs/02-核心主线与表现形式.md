# 事证 EventProof · 核心主线与表现形式

> 目的：把“做什么”收敛成一条可演示、可验收的主线；避免做成资讯流或聊天机器人。

## 1. 一句话主线

**一条消息进来 → 判断它是不是同一事件的新版本 → 拆成可核验的主张 → 给每条主张绑定证据和权重 → 推导事件当前状态 → 实质变化时通知用户 → 支持按“当时已知”回放。**

这条主线的主角不是“文章”，是**事件的当前结论 + 它的证据链 + 它的版本历史**。

## 2. 主线只回答四个问题

| 用户问题 | 产品动作 | 主要界面 | 证据 |
| --- | --- | --- | --- |
| 这是不是同一件事？ | 合并重复报道；关联同一 storyline 的不同阶段；必要时拆分 | 事件详情、合并审核 | 实体、时间、关键槽位、LLM 同一性裁决 |
| 哪些是事实，哪些只是说法？ | 把文档拆成 claim，标注事实/观点/推测/传闻/否认/更正 | 主张区 | 原文 quote、来源层级、hedge 词 |
| 现在是什么状态，凭什么？ | 计算证据强度，识别冲突，推导核实状态 | 结论卡、冲突面板 | 权重拆解、独立来源、传播链 |
| 什么时候变的，变了什么？ | 生成 revision、diff、通知 | 版本、通知中心 | knowledge_at、触发文档、变化原因 |

再加一个“信任动作”：**如果回到当时，我们只知道什么？** → as-of 回放。

## 3. 英雄场景（演示脊柱）

只选一个真实事件，把它讲透，而不是逐个功能参观。

以“A 公司收购 B 公司”为例：

| 时间 | 发生什么 | 系统应该怎么表现 |
| --- | --- | --- |
| 10-15 | 媒体称“据传 A 拟以 12 亿元收购 B” | 新建事件；claim 标为 rumor；证据强度低；不推送 |
| 10-17 18:30 | A 发布公告：拟以 8 亿元收购 B 100% 股权 | 同一事件挂接；新增 fact；金额 12 亿被标记为“与公告不一致”；状态从 unverified → confirmed（或 disputed，取决于原文） |
| 10-18 09:10 | A 发布澄清：否认 12 亿元传闻，确认 8 亿元 | 新增 denial；原 rumor 标为“已否认”；生成 revision diff；P0 通知 |
| 任意时刻 | 用户拖动 as-of 到 10-17 20:00 | 只能看到当时的传闻 + 公告，不出现 10-18 的澄清；证明结论不是事后编的 |

这一个事件同时覆盖：同一事件合并、claim 分类、证据权重、冲突、状态迁移、版本 diff、通知、回放。演示视频只讲这一条线。

## 4. 表现形式

### 4.1 产品形态

**桌面优先的研究工作台，不是聊天窗口。**

- 左侧：关注标的 / 事件收件箱，按“实质变化”排序，不按发布时间堆资讯。
- 中间：事件详情（结论卡 + 双时间轴 + 主张分组 + 冲突 + 影响）。
- 右侧：证据抽屉（原文高亮、来源层级、抓取时间、权重拆解、传播链）。
- 顶部：as-of 时间滑块；进入回放后，所有未来证据自动隐藏。
- 弹层：版本 diff（新增/修改/删除的 claim、状态变化、触发文档）。

聊天只能作为 P1 的“问一句”入口，不能成为主界面。用户需要的是可审计的状态，不是一段无法回查的答案。

### 4.2 线框

```text
┌────────────────────────────────────────────────────────────────────┐
│ 事证 EventProof      关注 3   收件箱 4      As-of: 10-18 12:00  [回放]│
├──────────────────┬─────────────────────────────────────────────────┤
│ 事件收件箱        │ A公司收购B公司        [已否认] [进行中] [已反应] │
│ ● 官方否认12亿…   │ 一句话：公司否认12亿传闻；公告对价为8亿元        │
│ ○ 收购协议签署…   │ 证据强度 82/100   最后更新 10-18 09:10          │
│ ○ 业绩预告…       │ ┌ 事情发生 ────────────────────────────────┐   │
│                  │ │ 10-15 传闻   10-17 公告   10-18 澄清      │   │
│                  │ └ 我们得知 ────────────────────────────────┘   │
│                  │ 事实 3 | 观点 2 | 推测 1 | 传闻 2 | 冲突 1      │
│                  │ [时间线] [主张] [证据] [版本] [影响]             │
├──────────────────┴─────────────────────────────────────────────────┤
│ 证据抽屉：原文 quote / 来源层级 / 抓取时间 / 权重拆解 / 传播链      │
└────────────────────────────────────────────────────────────────────┘
```

### 4.3 视觉语言

- 状态色：确认=绿，未核实=琥珀，否认=红，更正=紫，过期=灰。
- 证据强度：小条形 + 分数 + “为什么”拆解；明确写“不是真值概率”。
- 来源层级：监管/交易所、公司官方、财经媒体、研报、互动问答、匿名传闻。
- 时间：每个时间后带精度徽标（日/时/分），推断时间标“推断”。
- 引用：每个数字/结论旁有脚注标记，点击打开原文高亮。
- 动效：只在“新版本到达”时做一次 diff 高亮，不做花哨动画。

### 4.4 页面优先级

| 优先级 | 页面 | 作用 |
| --- | --- | --- |
| P0 | 事件详情 / 结论卡 | 5 秒看清现在怎么样 |
| P0 | 双时间轴 + 主张 + 证据抽屉 | 30 秒看清凭什么 |
| P0 | 版本 diff + 通知中心 | 看清什么时候变了、为什么通知 |
| P0 | as-of 回放 | 证明不是事后编的 |
| P0 | 证据包导出 | 关键数字可追溯、可交付 |
| P1 | 事件收件箱 | 日常入口；P0 可以先做简化版 |
| P1 | 合并审核 | 展示同一事件判断的可控性 |
| P1 | 影响验证 | 行情/财务作为事件影响的旁证 |

### 4.5 备选形态：事件串（BBS 结构）

**结论：可以采用，但要做成“有版规的证据帖”，不是股吧。**

论坛的阅读节奏非常适合“同一事件持续演化”：主题帖、楼层、引用、置顶、编辑记录，用户一眼就懂。问题在于，论坛天然奖励“最新、最热、最会起标题”的帖子，而投资事件需要的是“最可信、最独立、最可追溯”的证据。

| BBS 元素 | 映射到产品 | 必须改掉的地方 |
| --- | --- | --- |
| 主题帖 | 事件 / storyline | 标题不能由用户起，必须由事件命题生成 |
| 楼主 | 最初来源 | 不是“楼主最大”，官方更正可以推翻原帖 |
| 楼层 | 一次披露 / 一条 claim | 默认按披露时间，不按“最新回复” |
| 引用 | 证据支持/反驳关系 | 引用必须落到原文 quote，不是只引用一句话 |
| 置顶 | 当前结论卡 | 由规则和最新 revision 生成，不能被回帖顶掉 |
| 编辑记录 | 版本 diff | 只追加、不覆盖；旧版本永远可回放 |
| 转载 | 同一来源的重复报道 | 自动折叠，只算一个独立来源 |
| 锁帖 | 已过期/已归档 | 仍可查看历史，不删除 |
| 版规 | 证据规则 | 每条必须有来源、时间、类型；传闻必须标注 |

**不要做的**：

- 不做用户发帖、评论、点赞、热度排序；这里的“帖”是来源文档，不是 UGC。
- 不做匿名爆料；没有来源的“听说”不进入事件串。
- 不做“最新回复”置顶；最新不等于最重要。
- 不做论坛皮肤（头像、签名、表情包）；保留结构，去掉江湖气。
- 不让“楼主”天然正确；官方澄清、更正、撤稿都可以改变结论。

**推荐形态：事件详情默认用“事件串”，顶部固定结论卡。**

```text
┌────────────────────────────────────────────────────────────────────┐
│ A公司收购B公司        [已否认] [进行中]   证据强度 82   [简报|事件串] │
├────────────────────────────────────────────────────────────────────┤
│ 📌 当前结论（系统置顶，随证据更新）                                 │
│ 公司否认12亿元对价传闻；公告披露的对价为8亿元。                      │
│ 依据：公告 10-17 18:30 · 澄清 10-18 09:10        [查看版本 diff]    │
├────────────────────────────────────────────────────────────────────┤
│ #01  最初来源  财经媒体A   10-15 09:20   [传闻] 强度 28             │
│ “据市场消息，A拟以12亿元收购B…”                         [原文]      │
│      └ 转载 8 篇 · 独立来源 1 个                         [展开]      │
│ #02  公司公告  交易所      10-17 18:30   [事实] 强度 93             │
│ “拟以人民币8亿元收购B公司100%股权…”                     [原文]      │
│      └ 与 #01 金额冲突：12亿 vs 8亿                      [冲突]      │
│ #03  官方澄清  公司        10-18 09:10   [否认] 强度 96             │
│ “上述12亿元对价传闻不属实…”                             [原文]      │
│      └ 引用 #01 · 状态变更：未核实 → 已否认               [diff]     │
├────────────────────────────────────────────────────────────────────┤
│ 版本记录：10-18 09:10 系统更新 · 触发文档 #03 · 通知已发送           │
└────────────────────────────────────────────────────────────────────┘
```

这个形态的好处：

- 用户不需要理解“claim graph”，也能顺着楼层看懂事情怎么演化。
- “置顶结论 + 楼层证据”同时满足“快速看结论”和“慢慢看依据”。
- 转载折叠、引用、编辑记录天然对应同一事件合并、证据关系和版本。
- 演示视频更有叙事性：一楼一楼往下看，最后官方澄清出现，置顶结论翻转。

风险：

- 太像论坛会被误认为舆情产品；所以视觉上要像“案卷/研究笔记”，不是“股吧”。
- 楼层顺序会诱导“越新越真”；所以默认按披露时间，但提供“按证据强度”排序，且置顶结论独立于楼层。
- 论坛感会让人期待“评论”；明确写“本串只收录来源与证据，不开放用户评论”。

## 5. 演示视频（90–120 秒）

| 时间 | 画面 | 一句话 |
| --- | --- | --- |
| 0–15s | 收件箱 | “关注 3 只票，昨晚 4 条实质变化，17 条重复转载被折叠。” |
| 15–40s | 事件详情 | “同一件事从传闻到公告，四个时间分开记。” |
| 40–65s | 主张/证据 | “12 亿是传闻，8 亿是公告；点开原文，权重差在哪里。” |
| 65–90s | 澄清公告到达 | “状态从待核实变成已否认；diff 只显示真正变了的字段。” |
| 90–110s | as-of 回放 | “回到 10-17 晚上，只能看到当时已知的证据。” |
| 110–120s | 影响/导出 | “市场反应只是旁证；一键导出证据包。” |

## 6. 10 元模型预算怎么花

### 6.1 原则

**预计算，不在部署时调用模型。** 10 元买的是“把演示语料跑一遍”的一次性成本，不是在线产品的长期推理成本。

### 6.2 预算分配

| 用途 | 预算 | 说明 |
| --- | --- | --- |
| Claim 抽取 + 类型分类 | 6 元 | 40–60 篇文档，标题 + 导语 + 相关段落，不整篇 PDF 硬塞 |
| 同一性/冲突裁决 | 2.5 元 | 只对 top-10 候选对做裁决，不做全量两两比较 |
| 摘要 + 通知文案 | 1.5 元 | 8–12 个事件，每个 1–2 次调用 |
| 重试/难例 | 含在上面的硬上限内 | 总花费硬停 8 元，留 2 元缓冲；超过就降级到规则 |

按当前低价中文模型的量级，40–60 篇文档、150–300 条 claim、30–50 次裁决，10 元通常够用；具体以实际账单为准，不把估算当承诺。

### 6.3 模型选择

- 抽取/分类：便宜的通用中文模型（如 Qwen-Flash、DeepSeek-chat 一类），temperature=0，JSON schema。
- 裁决/摘要：同一档模型加更强 prompt；不必上最贵模型。
- Embedding：40–60 篇文档不需要付费 embedding；用实体/时间 blocking + 标题 trigram + 可选本地 bge-m3。
- 不把 GPT-4 级模型用于批量抽取；只在极少数争议样本上人工复核。

### 6.4 成本护栏

- `MAX_SPEND_CNY=10`，`HARD_STOP_CNY=8`；每次调用记录 tokens/cost。
- 按 `content_hash` 缓存；同一文档不重复抽取。
- 输入截断：标题 + 导语 + 命中 claim 的段落，控制单次输入。
- 失败重试最多 2 次；仍失败走规则抽取，界面标 `degraded`。
- `llm_calls` 表记录模型、prompt 版本、输入 hash、输出、耗时、费用；管理页显示“已花 / 剩余”。
- 预算耗尽不影响演示：预计算产物已入库，页面继续可读。

### 6.5 10 元买不到什么

- 买不到全市场实时抽取；
- 买不到长文档全文反复推理；
- 买不到高并发在线问答；
- 买不到模型微调。

这些都不在 48 小时演示范围内。演示要的是“一条事件线讲透”，不是“全市场覆盖”。

## 7. 设计取舍

- 不做资讯流：资讯是原料，事件才是产品对象。
- 不做聊天优先：聊天无法承载版本、冲突和证据链。
- 不做“真值机器”：产品输出的是证据强度和当前状态，不是“真相判决”。
- 不做全市场：3–5 个标的、8–12 个事件，把一条线做深。
- 不把 AI 当装饰：AI 负责抽取、分类、裁决、摘要；规则负责评分、状态和通知。

## 8. 下一步

1. 冻结一个真实“收购 + 澄清”事件作为英雄场景。
2. 先做事件详情（结论卡 + 双时间轴 + 主张 + 证据），再做收件箱。
3. 用 10 元预算离线跑 claim/裁决/摘要，产物入库。
4. 做 diff + 通知 + as-of 回放，这是演示的“啊哈时刻”。
5. 最后补影响验证、合并审核、数据健康和证据包导出。
